## 本人判断

建议先将本批交讨论 Chat 复核，暂缓把当前冻结版直接推进两套全量正式比较。相对最近全量版本，新方法确实把更多已知金融风险线索落实为持有人效果和可计分的主报警；相对作为主要参照的 v32，金融侧没有新增风险版命中，并丢失12个既有命中。AC 对 v32 有小幅净增，但误报总数持平，且同成员上弱于最近全量方法。以下结论限于按 v32 历史差错富集的开发批。选择未使用本次输出；17份与前一轮100份重合。即使不改变样本，前态、模型服务和方法合同的差异也妨碍单组件归因。

* **真正的新增。** RQ1_4580c60aec2d 的 TokenERC20 在两项主要参照中都漏检。本版短答指出它是公开普通初始化函数，宿主将权限关系落实到同一入口的性质和有界核查，最终命中。RQ1_9aafb6cd1add 的最终锚点是 transferOwnership，但被采用的回答明确将问题归到公开的 Owned2 重置角色，依既有下游表现归回取得权限根因。
* **保留不利证据。** RQ1_e85ac4a50ee4 的原答和反馈都定位到 kill 及终止条件，结果止于 expected_authorization_not_established；RQ1_2be3e9b98fac 已有初始化风险主张，止于 authorization_violation_not_established。这两种失败分别发生在性质建立和违反条件的核查。最近全量丢失的9根中，7根所在成员本版为未知，另外2根所在成员有其他报警。仅凭合约“有报警”会漏掉该退化。
* **误报未得到整体改善。** 80份中41份有 AC 报警，39份未知，没有有效的合约级 AC 不报。v32 有22个旧 FP 组所在的14份成员现为未知，最近全量方法有21个旧 FP 组所在的14份成员现为未知。不能把这些消失的报警计为纠错；仍有其他报警的成员也须按具体原因区分。evaluation/AC_FP_Transitions.json 保留三项历史方法的旧组与新组，组ID只在各自方法内有意义。
* **权限语义与公式主体的偏差有实证。** 43个 FP 组中有17组至少一条 finding 使用了标为 normal_authorization 的业务解释。以 RQ1_2c07fdcf80d4 的 approve 为例，短答说明持有人设置自己的 allowance，而正查询把资格主体编译成存储声明 admin（AST 94）。在这个公式下满足“调用者不是 admin”不回答持有人能否为自己授权。重复的两个继承目标只计一个 FP。另一个成员 RQ1_c9a2d9b618a7 的普通 transfer 被绑定到 founder（AST 376）。原始语义、主体声明、正查询和根因裁决列在 AC_PropertyAudit.json；不能据此断言全部43个 FP 都有同一成因。
* **位置相同也可能判分不同。** RQ1_868007cf433c 同一 fallback 有两条主报警。关于阈值后公开销毁的一条符合作者原注，虽其模型原判为正常，基准仍计 TP，业务政策正确性另存争议。另一条说零参数导致不可用，计 FP。RQ1_f91e2b168fdf 虽报在 Rasthen，却将其解释为正常部署构造过程，未指出 Incorrect Constructor，故该报警为 FP、作者根因为 FN。技术补充 RQ1_e6f04047bff4 产生的两条报警对应一个设备资格 TP 和一个余款 FP，另一个 CollectMoney 根因仍为 FN。

每类固定12份风险版、12份修复版。主 FN 为已判未检出和风险版未知之和；U−不计TN。F1等于2TP/(2TP+FP+FN)，五类等权平均。MINT 的 F1=1，同时有1份修复版未知，因此只有11对双边正确。总计风险未知11份、修复未知3份。另有17份材料合计30条其他类别的主报警；指定类别0个FP并不说明跨类别也没有误报，附加类别单独保留。

* **与最近一次实跑相比，改善主要发生在消费和核查。** 风险版新增21个命中、丢失1个，净增20个。21个新增中，19个此前为未知，2个是有效未检出。旧版在20个成员已有同类别提示或对应性质问题，其中19个已绑定到本版命中入口，4个甚至已产生同类别非主预测。新版在其中15个成员的全部指定类最终报警所关联条目仍标为 normal 或 investigate。改善不能概括为模型新找到了21个漏洞；也不能据两次完整方法的比较分配 LLM、状态域或求解器的独立收益。
* **改善集中在少数形态。** TRANSFER 从1/12升到11/12，11个命中均有 zero_fee_transaction 入口。源对比表确认11份报警入口均与风险/修复版改行重合。RQ1_3a3d833ca142的旧版就指出受角色控制的账本转移，但只记 unresolved；本版记录了同账本扣款和对应入账的 direct_effect，角色未激活的部署疑点另存。这支持条件性能力检测，不能推出一般资产转移或实际部署可达性。PAUSE 在代表例中从询问管理员能否设置开关，推进到比较持有人请求是否真正被阻断。逐个探针、所用前态和主报警关联见 cases/。
* **与 v32 相比，落差来自具体漏检。** 40个风险命中全部也是 v32 命中。v32 原来命中的12份被丢失，其中10份退为未知，2份明确未检出。60对中丢失13个原先双边正确的配对，没有新增整对正确。相对最近全量方法则新增24个整对正确，没有丢失其原有正确对。两个对照给出的结论不同。
* **显式阴性也可能判错。** 9个明确漏检中8个的指定类义务全部依据 source_effect_and_privilege_relevance 排除；57个有效 TN 中也有56个仅使用这项依据。后者照冻结口径计 TN，但该依据本身不足以证明系统学会了作者的修复。RQ1_353a9b0b5006 和配对修复版 RQ1_db11e3e08742 都提出销毁或费率扣减线索，在程序中都被构造成 PAUSE，两份 DESTROY 均为不报。它纠正了 v32 的一个修复版指定类 FP，同时丢失了对应风险版 TP。这是评分意义上的纠错，缺乏对该修复机制的有效区分。
* **FREEZE 和 PAUSE 的困难不同。** FREEZE 仍只命中4/12，和最近全量持平。8个未命中中有5个明确不报和3个未知，其中7个的规范化原答包含 FREEZE 类别，单靠增加提案条数解释不了这个缺口。RQ1_20dfd0c54b94 是 PAUSE 从旧 TP 变未知的实例，模型已指出特权开关和受影响人群；部分目标存在歧义，派生入口的金融阻断条件未成立，仍有27个未执行动作。记录能定位失败阶段，不能证明放宽约束一定能正确检出。
* **风险定义与前态。** 金融核查使用批准的条件性能力域。受冻结源约束的权限/余额在该域可以成立，部署后谁实际持有权限另记。相同源码和本批目标并不保证 v32、JANUS 作者工具和本方法使用同一初态。FCR_PairSourceAudit.json 对60对标出相关声明及改行，仅用于离线解释；没有用修复身份取消报警或改分。

## 工程可靠性与资源

主批200份都启动，198份直接出报告且均带有局部缺口。两份 AC 在首答及反馈均完成后因消费者类型错误中止。第一份修后复用原答得到0条报警，仍未知；第二份在修后重算时探针编号改变，直接套用旧反馈被拒绝。恢复原程序到收到反馈后才切换修后消费者，得到2条报警。两份都核对了原请求和回复；原失败、首次不匹配、主批和补充冻结清单都保留。全批最终200份有选定报告，不能称200份均为同一实现无故障实跑。

主批墙钟 4,676 秒（约1小时18分），共356次真实调用：200次首答、153次语义反馈、3次协议恢复，每份1或2次。6次因输出长度结束，5次没有有效正文。输入2,211,026、输出4,283,731 Token，总计6,494,757；其中推理3,993,294，已含在输出内。全部356次有用量回执，无在途或当批未知请求。按公开时段单价与真实用量核算为2.85—5.71美元，供应商账户实扣未提供。两份恢复无新增请求或模型费。历史未知用量保留。上一完整方法在同成员349次请求、5,396,392 Token、2.43—4.87美元；本次 Token 增加20.35%。v32 同成员200次、10,634,199 Token，模型别名和时期、默认输出合同、是否反馈均有差异，未推算同期账单。

## 放行判断及复核重点

若放行依据是相对 v32 的实际进步，本批尚未满足。AC 有新增根因，但同样保留了大量正常授权误报和未知；FCR 的收益对最近版本成立，对 v32 的风险版召回与整对正确均落后。建议讨论 Chat 优先复核三类可被证据推翻的判断：normal_authorization 是否真的被编译成不同主体；353a/db11 两份按类别计一错一对时是否共享同一个误判路径；TRANSFER 重复入口在换成不同账本结构后能否保留效果。本批没有对应的独立消融或未见数据，后两类的外推不能由本次成绩替代。本次未改方法、未重跑、未重评分历史记录。
